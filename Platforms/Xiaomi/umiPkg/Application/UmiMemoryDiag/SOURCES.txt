UmiMemoryDiag v4 — guarded RAM and Darwin-style allocation tests

SMEM region 0x80900000+0x200000 is already reserved and MMU-mapped in the
verified umi firmware; its address agrees with the handset FDT and XBL.
Candidate 0xc0000000..0xe0000000 is accessed only after independent
SMEM/FDT/EFI/GCD checks. Shared memory is read-only; the code does not
allocate shared-memory items or invoke vendor initialization.

Qualcomm's Aswin Murugan, U-Boot mailing-list patch, 2026-04-17:
https://www.mail-archive.com/u-boot@lists.denx.de/msg570801.html
"[PATCH v3 1/7] mach-snapdragon: Add generic SMEM cache infrastructure"
Proposed arch/arm/mach-snapdragon/rampart.h explicitly defines table version
0x3: 24-byte header, 72-byte entries, available_length at entry offset 64.
It is a submitted patch, not claimed as merged U-Boot code. The v3 wire
layout is independently decoded here; no source implementation is copied.
The observed umi item size 0x918 equals 24 + 32 * 72.

The FDT is obtained from the preserved entry-argument HOB and accepted only
inside the existing 0xa0000000..0xb0000000 mapped boot window, <=2 MiB.
EFI GetMemoryMap describes the allocator's actual current map; adjacent
conventional descriptors are combined for largest-run reporting only.

The probe also verifies the candidate is contained in exactly one FDT bank,
is disjoint from every static reserved-memory reg and FDT memreserve, is
absent from the current EFI map, and lies in a nonexistent GCD region.
The twelve observed size-only reserved-memory requests are matched by name,
size and allocation bounds. They are future Linux allocations, not current
physical carveouts: no Linux kernel has run in this temporary boot. No
arbitrary dynamic node is accepted. Unknown layouts fail closed.

After guards: establish a WB/XP MMU mapping, fill and check the entire
512 MiB twice using complementary address-dependent patterns, with cache
writeback/invalidation between fill and verify. Register only this range
using GCD services, set WB/XP, AllocatePages a contiguous 256 MiB within it,
repeat the patterns, FreePages, log the resulting map, and warm-reset.
If the firmware has already registered the candidate (attempt 19 onward),
the application verifies all covering GCD descriptors are system memory and
skips direct full-range writes and registration. It touches only pages
successfully allocated by UEFI, preserving the firmware's live allocations.
The v4 allocation uses AllocateAddress/EfiLoaderCode with the same 2 MiB
rounding and adjacent-descriptor merging requirement as DarwinBoot. It
tests two kernel low offsets, 0 and 0x4000, each with 256 MiB and both
patterns, and frees each allocation. This is an allocator qualification;
DarwinBoot, ExitBootServices and XNU entry have not run.
Test failures are logged and reset; external aborts still require manual
recovery. It is not a full DRAM stress test or proof of all boot-time users.
Runtime registration is inspired by Silicium MemoryAllocationHelperLib;
ArmSetMemoryAttributes uses this pinned Mu_Basecore API's EFI attributes.
No persistent partitions are written.

Host test: tests/test_umi_memory.py compiles the real parser with ASan/UBSan
and checks valid v11/v12, RAM v1/v2/v3, read-only operation and malformed
offsets/sizes/counts/padding. It does not establish hardware accessibility.
The external application is built but is never included in the firmware FV.
